## 1. 背景与问题陈述
### 1.1 市场痛点
当前系统级编程领域存在一个明显的断层：
- **C/C++**：生态无敌、零成本抽象，但内存安全问题（约 70% 的 CVE 源于内存安全缺陷，微软/谷歌多年数据）和未定义行为使工程成本极高；
- **Rust**：编译期保证内存安全，但所有权、借用、生命周期三大显式标注的学习曲线陡峭，社区公认“与借用检查器搏斗”是最大上手障碍；
- **Python**：极低上手门槛，但动态类型 + GC 使其无法胜任系统级场景（性能、确定性延迟、嵌入式）；
- **Mojo / Hylo / Roc 等新语言**：正在探索同一路线，但均未形成成熟生态或仍在早期阶段。
### 1.2 机会
**将“安全”与“好学”的对立转化为编译器复杂度与用户体验的交换**：把 Rust 中要求用户显式书写的所有权/借用/生命周期标注，全部下沉为编译器的自动推导；安全的保证不变，用户负担趋近于零。同时以 C ABI 为第一公民，使新语言可以直接继承 50 年的 C 生态，无需从零建设标准库。
### 1.3 一句话定位
> **编译期内存安全、无 GC、C 生态原生兼容、对 Python 使用者零门槛入门的系统编程语言。**

## 2. 目标与非目标
### 2.1 目标（Goals）
| # | 目标 | 可验证标准 |
|---|---|---|
| G1 | Rust 同级的内存安全 | 在安全子集内，禁止悬垂指针、use-after-free、double-free、数据竞争（编译期拒绝） |
| G2 | 零学习标注负担 | 入门教程不出现 `&`、`&mut`、生命周期标注；80% 的示例代码不含任何内存管理显式语法 |
| G3 | 无 GC | 运行时无垃圾回收线程、无 stop-the-world；释放点由编译器确定性插入（RAII 语义） |
| G4 | C 无缝互操作 | 直接调用未修改的 C 库；导出函数可被 C 代码直接链接；FFI 调用零运行时开销 |
| G5 | 竞争力性能 | 与 Rust 的基准差距 ≤ 10%（Benchmarks Game 选集） |
| G6 | 编译器错误即教学 | 错误信息包含：出错位置、原因、修复建议代码片段 |
### 2.2 非目标（Non-Goals）
| # | 非目标 | 理由 |
|---|---|---|
| N1 | 不做语法层设计决策 | 语法（缩进 vs 花括号、关键字命名等）另行立项，本 PRD 只约束语义 |
| N2 | 首版不做跨线程数据竞争检查 | `Send`/`Sync` 级别的并发安全列入 v2 |
| N3 | 不做 Python 源码级兼容（超集） | 只做 C ABI 兼容；Python 互通通过 FFI 桥后期提供 |
| N4 | 不做解释器/REPL 优先 | 首版即为 AOT 编译语言；REPL 列为 v2 开发体验项 |
| N5 | 不自研后端 | 使用 LLVM，不自建代码生成器 |

## 3. 目标用户与场景
### 3.1 用户画像
| 画像 | 描述 | 核心诉求 |
|---|---|---|
| **P1：从 Python 进阶的工程师** | 写过数据脚本/后端，遇到性能墙 | 想要“还是那个写法，但快 100 倍、不再有 GIL” |
| **P2：被 Rust 劝退的系统程序员** | 有 C/C++ 经验，试过 Rust 后放弃 | 想要内存安全但不想背所有权规则 |
| **P3：嵌入式/底层开发者** | 维护 C 代码库，无法引入 GC | 需要零开销、确定性内存、直接复用 C 库 |
### 3.2 关键场景
- **S1**：P1 用户用本语言重写一个 Python 热点模块，调用现有 C 加速库，全程不接触指针概念；
- **S2**：P3 用户在现有 C 项目中，用本语言编写一个新模块并编译为 `.o` 直接链接进原有构建系统；
- **S3**：P2 用户通过 bindgen 工具为 sqlite3/zlib 生成绑定，在安全代码中直接调用，无需手写 unsafe。

## 4. 需求详述
### 4.1 功能需求
#### FR-1 类型系统
| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-1.1 | Hindley-Milner 风格类型推断：函数体内部变量、表达式类型全部自动推断，无需标注 | P0 |
| FR-1.2 | 公共 API（导出函数签名、公开 struct 字段）要求显式类型标注 | P0 |
| FR-1.3 | 仿射类型底座：非 Copy 类型每个值最多一次使用，使用即 move，move 后访问编译报错 | P0 |
| FR-1.4 | `Copy` 自动派生：编译期大小 ≤ 2 机器字且所有字段可复制的类型自动为 Copy，用户不可干预 | P1 |
| FR-1.5 | 代数数据类型：struct、enum（含 tag union）、`Result`/`Option` 内置 | P0 |
| FR-1.6 | 默认值语义：赋值/传参为逻辑拷贝，物理拷贝或原地修改由编译器决定；引用语义需显式包装类型 | P1 |
| FR-1.7 | 泛型 + trait（静态分发默认，动态分发显式），支持单态化 | P2 |
#### FR-2 自动借用推导（本产品的核心差异化）
| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-2.1 | 参数约定自动推导：编译器按流敏感分析为每个参数选择 `borrowed`/`inout`/`owned`，用户默认不写 | P0 |
| FR-2.2 | 推导规则：仅读 → borrowed；存在写路径 → inout；被存储/返回/转移 → owned | P0 |
| FR-2.3 | 冲突消解：同一变量的读写冲突按独占写规则分割生命周期区间（NLL 等价语义） | P0 |
| FR-2.4 | 生命周期为编译器内部区域变量，通过 region inference 求解，不进入用户可见语法 | P0 |
| FR-2.5 | 显式覆盖通道：用户可用最短语法强制指定约定（如传值转移符号），用于消歧和性能微调 | P1 |
| FR-2.6 | 推导诊断：借用冲突报错必须输出推导依据（“此参数被推导为可变借用，因为第 N 行写入了它”）及修复建议 | P0 |
| FR-2.7 | 跨过程推导：已导出函数的推导结果固化为签名契约并缓存，调用方直接使用 | P2 |
#### FR-3 内存管理（无 GC）
| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-3.1 | 栈分配优先：编译期已知大小的值默认栈分配 | P0 |
| FR-3.2 | 确定性析构：编译器基于活跃区间在 CFG 上自动插入 drop 调用，作用域结束语义与 RAII 一致 | P0 |
| FR-3.3 | 用户自定义 `Drop`：析构函数按逆序确定性执行，可用于包装 C 资源（文件句柄、连接等） | P0 |
| FR-3.4 | 堆分配类型（Vec/String/Box 类）编译期证明唯一 owner，释放点唯一 | P0 |
| FR-3.5 | drop 插入优化 pass：合并、消除 Copy 类型 drop、内联平凡 drop | P1 |
| FR-3.6 | 运行时保证：无 GC 线程、无引用计数元数据、无运行时安全检查（safe 子集零运行时开销） | P0 |
#### FR-4 C 互操作
| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-4.1 | `extern "C"` 导出：生成未 mangle 符号 + 自动产出 C 头文件 | P0 |
| FR-4.2 | C 类型映射：固定宽度整数/浮点/指针与 `stdint.h` 一一对应；`#[repr(C)]` struct 布局与 C 一致 | P0 |
| FR-4.3 | bindgen 工具：解析 C 头文件自动生成安全绑定（基于 libclang） | P1 |
| FR-4.4 | 不透明指针类型：封装 `sqlite3*` 类句柄，禁止直接解引用，强制经包装器访问 | P1 |
| FR-4.5 | 跨界所有权规则：非 POD 类型跨界需显式 `into_raw`/`from_raw` + 配对释放函数 | P1 |
| FR-4.6 | unsafe 边界：裸指针操作、直接解引用、任意 C 调用仅限 unsafe 块；纯计算型 C 库可通过审查标注在安全代码直接调用 | P1 |
| FR-4.7 | 引用出借给 C 的生命周期检查：禁止 C 调用持有本语言引用逃逸 | P2 |
#### FR-5 工具链
| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-5.1 | 编译器单命令构建：`build` 一键从源码到静态库/动态库/可执行文件 | P0 |
| FR-5.2 | C 项目集成：产物为标准 `.o`/`.a`/`.so`，可嵌入 Makefile/CMake | P0 |
| FR-5.3 | 错误诊断系统：位置、推导过程、修复建议三段式输出 | P0 |
| FR-5.4 | 包管理 + C 库依赖声明（链接系统库/源码编译 vendored C） | P2 |
### 4.2 非功能需求
| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-1 | 运行时性能 | 与等价 Rust 代码差距 ≤ 10%（选定基准集） |
| NFR-2 | 编译性能 | 中型项目（5 万行）全量编译 ≤ 30s（参照本机 rustc 对照） |
| NFR-3 | 产物体积 | hello world 静态二进制 ≤ 1MB |
| NFR-4 | 可移植性 | 首版支持 linux-x86_64；v1 扩展 aarch64、macOS、Windows |
| NFR-5 | 安全子集完备性 | 通过 cirque-style 借用检查测试集；模糊测试发现的 safe 子集 UB 数为 0 |
| NFR-6 | 学习成本 | 熟悉 Python 的工程师 1 天内能编写并调试通过 C 互操作示例 |

## 5. 技术方案概要
### 5.1 编译器架构
```
源码 → 前端 → HM 类型推断
     → MIR + SSA 构造
     → 借用推导 pass（borrowed/inout/owned 标定）
     → region inference + 逃逸分析
     → drop 插入 pass
     → LLVM IR → 机器码 / 静态库 / 动态库
```
关键决策：
1. **借用检查在 MIR/SSA 层做，不在 AST 层做**——复用 SSA def-use 链，实现难度大幅低于语法树方案（吸收 rustc 的成熟经验）；
2. **借用检查与类型检查解耦**——先完成完整类型推断，再做所有权/借用分析，两阶段错误不互相污染；
3. **后端直接采用 LLVM**，C ABI 天然兼容，导出符号即标准 C 调用约定。
### 5.2 自动借用推导算法（核心 IP）
1. 初始化：所有参数假设为 `borrowed`（最小特权）；
2. 函数体 SSA 化后做流敏感扫描，按 FR-2.2 规则升级约定；
3. 读写冲突按“并发读/独占写”策略分割借用区间；
4. 导出函数的推导结果缓存为 ABI 契约。
### 5.3 与竞品的差异化锚点
| | 本语言 | Rust | Mojo | Hylo |
|---|---|---|---|---|
| 内存安全 | ✅ 编译期 | ✅ 编译期 | ✅（迭代中） | ✅ |
| 借用/生命周期标注 | ❌ 全自动 | ✅ 必须手写 | 部分（fn 需标注约定） | ❌（值语义路线） |
| C ABI 双向原生 | ✅ P0 | ✅ | ⚠️ 侧重 Python | ❌ |
| 生态冷启动策略 | 复用 C | 自建 | 依附 Python | 自建 |

## 6. 里程碑规划
| 阶段 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0：垂直切片** | 3 个月 | 显式标注版语言（需手写 `&`/`&mut`）+ LLVM 后端 + C 导出 | 能编写调用 zlib 的程序并正确链接运行 |
| **M1：MVP** | +4 个月 | HM 推断 + 过程内借用推导 + drop 插入 + bindgen 原型 | FR-1.1/1.3、FR-2.1~2.3/2.6、FR-3.1~3.4、FR-4.1/4.2 全部达标 |
| **M2：自举候选** | +6 个月 | 跨过程推导 + RAII 资源管理完善 + 诊断系统成型 | 30 个真实 C 库绑定案例通过；性能基准达到 NFR-1 |
| **M3：公测** | +6 个月 | 包管理 + 文档 + 教程（零标注入门路径） | 10 个外部早期用户完成 S1~S3 场景验证 |
**M0 的关键解耦决策**：先用显式标注跑通全链路（编译器骨架、LLVM、C ABI 均可独立验证），再开启自动推导。编译器实现与推导算法两条线并行推进，互不阻塞。

## 7. 成功指标（North Star + 支撑指标）
- **North Star（M2 时点）**：入门教程全部示例中，显式内存管理语法出现率 ≤ 20%，且编译期拒绝全部注入的内存安全违例用例（自建测试集 ≥ 100 例）；
- 支撑指标：S2 场景中 C 项目集成步骤 ≤ 3 条命令；NFR-1~6 全部达标；核心推导 pass 的单元测试覆盖率 ≥ 85%。

## 8. 风险与对策
| 风险 | 等级 | 影响 | 对策 |
|---|---|---|---|
| **推导精度困境**：过保守则频繁要求显式干预（退化为 Rust 体验），过激进则拒绝合法程序 | 高 | 直接决定产品成败 | M1 只做过程内保守推导，收集真实误报样本迭代；保留显式覆盖通道作为用户逃生舱；参考 Mojo 公开的推导权衡记录 |
| C 边界安全豁免标准失准（`#[safe_c]` 形同虚设或误伤） | 高 | 安全承诺被击穿 | 豁免白名单从严起步（只放行无指针参数、无堆返回的纯函数）；建立标注审查清单 |
| 跨过程推导复杂度超预期 | 中 | 延期 | 降级预案：M1/M2 仅过程内推导 + 签名固化，跨过程全局求解推迟到 M3 后 |
| 错误诊断质量不足导致“自动推导失败时更难懂” | 中 | 用户体验反噬 | 诊断系统作为 P0 需求与推导 pass 同步开发，每个推导失败分支必须有对应的人话解释 + 修复建议 |
| 生态冷启动（无包、无库） | 中 | 早期用户流失 | 以 C 互操作为核心冷启动策略——绑定生成器让任意 C 库在数分钟内可用 |
| LLVM 编译速度不达标 | 低 | 开发体验差 | NFR-2 设为硬指标；必要时引入增量编译（远期） |

## 9. 待决策项（Open Questions）
1. 值语义默认（Hylo 式）还是所有权默认（Rust 式 + 自动推导）？**当前倾向**：值语义默认 + 引用显式包装，最大化消除标注——需在 M1 用真实代码库验证误报率后定稿；
2. 线性引用计数兜底（Perceus 式）是否进入 v1，用于编译器无法静态证明唯一性的图结构场景？
3. 推导失败时的默认报错策略：直接报错并给建议，还是自动插入克隆并输出警告（ ergonomic 路线，但隐式性能开销）？
