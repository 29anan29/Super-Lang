# M0 垂直切片实施计划

## 目标

3 个月内完成：从源码到可执行文件的完整链路。用显式标注（手写 `&`/`&mut`）实现，确保编译器骨架、C 编译器、C ABI 三条线独立可验证。

## 时间规划

| 周次 | 任务 | 交付物 |
|------|------|--------|
| 1-2 | 项目初始化、环境搭建、构建系统 | 可运行的构建脚本 |
| 3-4 | 词法分析器 | Token 流输出器 |
| 5-6 | 语法分析器 | AST + 解析器 |
| 7-8 | HM 类型推断 | 类型检查器 |
| 9-10 | MIR/SSA 构造 | SSA 中间表示 |
| 11-12 | C 代码生成器 | C 源码输出器 |
| 13-14 | 后端集成（gcc/clang） | 可链接的 .o 文件 |
| 15-16 | C 导出 + 头文件生成 | .h 头文件 |
| 17-18 | 错误诊断系统 | 三段式错误输出 |
| 19-20 | 测试 + 集成验证 | 完整工具链 |
| 21-24 | 调用 zlib 验证 | 端到端可运行程序 |

## 详细任务

### 阶段一：词法分析（周 1-4）

#### 目标

将源码字符串转换为 Token 流。

#### 具体工作

1. 定义所有 Token 类型（关键字、标识符、字面量、运算符、分隔符）
2. 实现 Lexer 类：逐字符扫描，按规则匹配 Token
3. 实现关键字表：标识符匹配时先查关键字
4. 实现字符串解析：支持转义字符
5. 实现注释解析：单行 `//` 和多行 `/* */`
6. 错误处理：非法字符报告位置和类型
7. 输出：Token 流（文件名、行号、列号、类型、值）

#### 验收标准

- 能正确解析所有 SUPER 关键字
- 能识别所有字面量类型
- 非法字符能报告精确位置
- 单元测试：100+ 个测试用例

### 阶段二：语法分析（周 5-6）

#### 目标

将 Token 流转换为 AST。

#### 具体工作

1. 定义所有 AST 节点类型
2. 实现递归下降 Parser
3. 实现每个语法结构的解析函数：
   - `parse_fn()` — 函数定义
   - `parse_struct()` — 结构体定义
   - `parse_enum()` — 枚举定义
   - `parse_if()` — if/else
   - `parse_for()` — for 循环
   - `parse_match()` — match 表达式
   - `parse_unsafe()` — unsafe 块
   - `parse_import()` — import 语句
   - `parse_extern()` — extern "C" 块
4. 错误恢复：跳过当前语句继续解析
5. 错误诊断：报告位置、期望内容、实际内容
6. 输出：完整的 AST

#### 验收标准

- 所有语法结构能正确解析
- 非法程序能报错并继续
- 错误位置信息精确
- 单元测试：150+ 个测试用例

### 阶段三：HM 类型推断（周 7-8）

#### 目标

函数体内部变量、表达式类型全自动推断。

#### 具体工作

1. 实现类型环境（Γ）：变量名到类型的映射
2. 实现约束生成器：遍历 AST 生成类型约束
3. 实现合一算法：求解约束集合
4. 实现类型规则：变量、函数调用、二元运算、函数定义、泛型
5. 实现泛型支持：单态化
6. 错误诊断：类型不匹配、未推断出类型
7. 公共 API 要求显式类型标注
8. 输出：带类型标注的 AST

#### 验收标准

- 基础类型推断正确（int、float、bool、string）
- 泛型函数能正确推断
- 类型错误能精确报告
- 单元测试：100+ 个测试用例

### 阶段四：MIR/SSA 构造（周 9-10）

#### 目标

将带类型标注的 AST 转换为 SSA 形式的中间表示。

#### 具体工作

1. 定义 MIR 指令集
2. 实现 CFG 构建：基本块 + 控制边
3. 实现 SSA 转换：每个变量只能赋值一次
4. 实现 φ 节点插入：控制流交汇处的值合并
5. 实现活跃区间分析：为后续借用推导做准备
6. 输出：MIR + SSA 表示

#### 验收标准

- 所有语法结构能转换为 MIR
- SSA 形式正确（每个变量单赋值）
- φ 节点位置正确
- 单元测试：80+ 个测试用例

### 阶段五：C 代码生成器（周 11-12）

#### 目标

将 MIR/SSA 转换为 C 源码。

#### 具体工作

1. 定义类型映射表：SUPER 类型 → C 类型
2. 实现代码生成器：MIR 指令 → C 语句
3. 实现函数生成：SUPER 函数 → C 函数定义
4. 实现表达式生成：运算符、函数调用、字段访问
5. 实现变量声明和作用域管理
6. 实现控制流生成：if/else、for 循环
7. 输出：C 源码文件（.c）

#### 验收标准

- 生成的 C 代码能通过 gcc 编译
- 生成的代码逻辑正确
- 类型映射正确
- 单元测试：100+ 个测试用例

### 阶段六：后端集成（周 13-14）

#### 目标

调用 gcc/clang 完成最终编译。

#### 具体工作

1. 配置 gcc/clang 调用
2. 实现编译流程：.c → .o
3. 实现链接流程：.o → 可执行文件/库
4. 支持优化级别（-O0, -O1, -O2）
5. 支持目标架构配置（x86_64 Linux）
6. 输出：`.o`、`.a`、`.so` 文件

#### 验收标准

- 生成的 .o 能被 gcc 链接
- 可执行文件运行正确
- 静态库和动态库生成正常
- hello world 静态二进制 ≤ 1MB

### 阶段七：C 导出与头文件生成（周 15-16）

#### 目标

SUPER 函数可被 C 代码调用。

#### 具体工作

1. 实现 `export "C"` 标记识别
2. 实现符号名称处理：生成未 mangle 符号
3. 实现 C 头文件生成器：生成 `.h` 文件
4. 实现类型映射：SUPER 返回值 → C 返回值
5. 实现变长参数支持
6. 输出：C 头文件 + 目标文件

#### 验收标准

- 导出的符号可被 gcc 直接链接
- 生成的头文件正确可用
- C 程序调用 SUPER 函数成功
- 单元测试：30+ 个测试用例

### 阶段八：错误诊断系统（周 17-18）

#### 目标

所有错误输出三段式信息。

#### 具体工作

1. 实现位置追踪：Token 级别源码位置
2. 实现语法错误诊断：位置 + 期望 + 实际
3. 实现类型错误诊断：期望类型 vs 实际类型
4. 实现借用错误诊断：推导依据 + 冲突位置 + 修复建议
5. 实现错误恢复：跳过错误继续解析
6. 彩色输出支持
7. `--verbose` 模式：显示详细推导过程
8. 输出：人话可读的错误信息

#### 验收标准

- 每种错误类型有对应的诊断格式
- 错误位置精确（文件名:行号:列号）
- 修复建议具体可用
- 单元测试：50+ 个测试用例

### 阶段九：测试与集成（周 19-20）

#### 目标

端到端验证完整链路。

#### 具体工作

1. 单元测试：各模块独立测试
2. 集成测试：完整编译流程测试
3. 边界测试：极端输入、错误处理
4. 性能测试：编译速度基准
5. 修复所有发现的 bug

#### 验收标准

- 核心模块单元测试覆盖率 ≥ 80%
- 集成测试全部通过
- 编译速度达标
- 错误诊断质量达标

### 阶段十：zlib 调用验证（周 21-24）

用 SUPER 调用 zlib 编写程序并正确链接运行。

#### 具体工作

3. 编译、链接、运行
4. 验证功能正确性

#### 验收标准

- zlib 函数能正确调用

- 功能验证通过
- **M0 里程碑达成**

## 技术依赖

- 编译器语言：C
- 构建工具：Makefile
- C 编译器：gcc 或 clang
- 解析器生成器：可选（手写递归下降）
- libclang：用于 bindgen（后续版本）

## 风险与对策

| 风险 | 对策 |
|------|------|
| 手写 Parser 复杂度高 | 先支持核心语法，逐步扩展 |
| SSA 构造困难 | 参考 rustc 的成熟方案 |
| C 代码生成质量 | 严格测试，生成后人工验证 |
| 编译速度不达标 | NFR-2 硬指标，持续优化 |
